# 検証方針

[AGENTS.md](../../AGENTS.md) および [GitHub 開発運用](github-workflow.md) と併用する。

## 検証の区別
- ローカル検証：使用した環境、対象 SHA、コマンド、終了結果を記録する。
- GitHub Actions：対象 SHA と実行 URL、各工程の結果を確認する。実行開始・完了・成功を区別する。
- 実 GUI 検証：実ブラウザで行った操作、ブラウザ種別、幅、日時、対象 SHA・URL、スクリーンショット等を記録する。HTTP 200、ビルド成功、ブラウザが開いたことだけでは操作確認にならない。
- 未実施・失敗：理由、確認できた範囲、代替手段と残る限界を明記する。コードを読んだことと実行したことは別である。

## 基本の検証
既存の単体テスト、lint、型検査、通常ビルド、Pages ビルドを基準とする。GUI の実行環境・コマンド・成果物は [e2e/README.md](../../e2e/README.md) を参照し、workflow と照合する。現在の PR GUI workflow は PR head を checkout するため、マージ結果や公開サイトを検証したと書かない。

GUI は GitHub Actions の隔離 runner と Playwright Chromium を継続利用する。Windows や新しい公開ホスティングを必須にしない。公開アプリの成功と修正ブランチの成功を区別する。自動 GUI は実ブラウザ操作だが、対話的 Cloud Browser 接続、iPhone Safari、全操作・全幅の保証ではない。

GUI が実行できない場合、接続・起動・権限などの具体的な原因を切り分け、既存の Pages preview や Actions 等の許可された代替を試す。安全制限を回避せず、必要な承認だけを尋ねる。代替の成功が元の未検証項目を満たすかを明示する。

## 失敗の診断
1. 対象 SHA、失敗した stage、exit code、ログ・trace・画面を保存する。
2. アプリの不具合 / テスト期待値や selector の誤り / 実行環境の問題を分ける。assertion 失敗だけで原因を断定しない。
3. 根拠に基づいて依頼範囲内の最小修正を行う。期待値は仕様の根拠なしに変えない。テストを無効化して成功扱いにしない。
4. 再検証し、初回失敗と修正後の結果を記録する。未解決ならそのまま報告する。

負の対照試験は通常変更と分離し、明示的に承認された隔離環境・ブランチで実施する。意図的な不具合を本番向け PR や main に混ぜない。ローカルでの失敗検出と、GitHub CI 全体での失敗伝播は別の実証である。

## 証拠・安全・限界
- 詳細ログや trace は CI artifacts 等を参照し、LOG.md には要点とリンクを記す。保持期限がある証拠はその制約を残す。
- 合成データと新規ブラウザ context を使用し、利用者の保存データ、秘密情報、認証状態を試験に持ち込まない。
- 既存 workflow の最小権限、秘密情報を渡さない PR 実行、本番公開との分離を維持する。fork の承認待ちや未実行を成功と報告しない。
- PR 内の workflow 自体は変更できるため、CI 成功だけを改ざん不能な安全証明と扱わない。コードレビューと照合する。
- 依存警告は到達性と用途を別途評価する。テスト成功だけで脆弱性なしと結論しない。
- GUI/CI の必須チェック化や保護設定は提案と実設定を区別し、承認なく変更しない。

## 最終確認
最終差分、LOG 更新要否、Issue/PR の関連、対象 SHA と CI、未検証・残件、main・本番への意図しない変更がないことを確認する。文書だけの PR でも起動した既存 CI の結果を確認する。省略した検証は理由付きで明記し、実施済みにしない。
