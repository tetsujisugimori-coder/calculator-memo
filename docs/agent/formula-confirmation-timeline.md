# 根拠・確認履歴タイムライン（Issue #67）

## 調査と範囲

基準は PR #66 merge 後の main `5cfee354167c51bf6d1021ef9df337bbae338291`。保存形式と検証経路を変更しない。

- 確実に表示できる事実: 保存された確認ID、登録式ID、関連レポートID、確認日時の原文字列、式/変数/タイトル/本文/根拠リンクの確認時snapshot、保存配列位置。これはブラウザ内の保存記録であり真正性や数学的証明の認定ではない。
- 条件付き: 検証済み取得原本との式定義/本文タイトル/リンク差分。根拠記録の照合は既存 `formulaReportAssessment` と `HistoricalReportEvidence` を使う。現在原本の取得失敗/外部更新後は一致判定をしない。過去記録の一致は現在確認への格上げではない。
- 記録不足: 実際の変更イベント、変更日時/理由、確認間の編集経過、式/レポートの版番号、当時の判定結果。updatedAtを変更履歴へ流用せず、不明を補完しない。履歴なし/旧形式もイベントを生成しない。

第一希望は変更を含むタイムラインだが、上記の情報不足により次善の「確認履歴中心+取得原本との差分」を採用。保存形式拡張による今後の変更イベント収集は今回不要、移行なし。確認履歴上限20件/既存容量制限も不変。

## 表示と順序

`formulaReportTimeline` は配列を複製して表示投影するだけで、保存原本の順序や確認履歴を変更しない。時差付き日時を全件解釈可能なら昇順、同一時刻は保存配列順。時計の正確性や同一時刻内の実際の先後は保証しない。既存validatorが受理する時差のない日時は補わず、全件を保存配列順で表示する。最後の確認記録は既存判定と同じ保存配列末尾であり、日時最大の記録を勝手に最新承認へしない。

`FormulaReportTimeline` は既存詳細内の縦型olとnative details/summaryで展開。履歴中の確認時状態は利用者の明示確認記録として説明し、当時の判定結果は記録なしとする。比較では式定義・本文タイトル・リンクの相違を別表示し、一つの相違で別の相違を隠さない。数学的同値性は判定しない。

取得日時は既存sharedsnapshotのfetchedAtを利用する表示情報で保存項目ではない。stale時は旧原本であることを明示し、対応判定/根拠記録詳細を抑止。既存loadData→readReportEvidenceが不正/未知履歴を拒否し、描画側も例外時は判定不能とする。writer/確認/再計算は呼び出さない。

## 検証と限界

単体: 安定順、同一時刻、時差不足、最後の保存記録、式/レポート/両方差分、履歴なし、未知・不正、未取得/欠落リンク、staleと明示再取得、原本不変。既存保存失敗/競合/キャンセル/未知保護の回帰も維持。
GUI: 既存6条件へタイムライン3検査ずつ追加。Chromium/WebKit、375/390px、両テーマ200%文字、キーボード、実他タブ更新/失敗/再取得を検査する。PNG114/30分/trace契約を変更しない。実機iPhone Safari/VoiceOverは未検証。実測結果はLOGとPRコメントに記録。

戻し方: 本差分のUI/表示投影/テスト/文書をrevert。保存データ移行・巻戻し不要。旧確認/保存保護は維持する。
