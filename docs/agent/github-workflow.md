# GitHub 開発運用

[AGENTS.md](../../AGENTS.md) を入口とする。現在有効な規則を優先し、[LOG.md](../../LOG.md) の過去の判断は証跡として読む。

## 着手と Issue
1. 最新 main の SHA、作業ツリー、README、関連 docs、workflow、open/関連 closed Issue・PR を確認する。他人の未コミット変更を巻き戻さず、同じ目的の作業があれば重複させない。
2. 目的・範囲・受入条件・対象外・既知の制約を整理する。複数段階、未解決問題、追跡が必要な設計判断には Issue を作成する。既存 Issue が該当すれば再利用・更新し、他者の記述を保持する。小さな独立変更は PR だけでもよいが、その理由を明記する。
3. Issue には現状、期待結果、完了条件、関連 PR、未解決事項を記す。ラベルや担当者は既存運用に従い、不要な通知や新設を避ける。

## ブランチ・commit・PR
- 最新 main から `feat/<短い目的>`、`fix/<短い目的>`、`docs/<短い目的>`、`test/<短い目的>` など用途が分かる枝名を選ぶ。既存作業を継続する場合はその枝の現状と基点を確認する。
- 範囲を絞って編集し、[検証方針](verification-policy.md) に従い確認する。main へ直接 push せず、履歴の強制書換えを通常手段にしない。
- commit 前に差分、秘密情報・実データの混入、LOG 更新を確認し、理由の分かるメッセージで commit、作業枝へ push する。
- PR 作成前に同一目的の PR がないか再確認する。原則 Draft で作成し、未検証や承認待ちを隠さない。既存 PR の変更・push は依頼範囲内で進める。
- 各 PR で原則 LOG.md を更新する。不要なら PR 本文に理由を記載する。PR 番号や結果が未確定なら未確定と書き、作成・検証後に事実を補う。詳細 CI ログはリンクを使う。

## PR 本文の必須項目
- 目的、変更内容、変更理由、対象外
- 関連 Issue（相互参照）と LOG.md の該当記録
- 自律的に判断した事項と理由、承認が必要な事項
- 検証結果：ローカル / CI / 実 GUI / 未実施を分け、対象 SHA・実行 URL・証拠を示す
- 未解決事項、残存リスク、戻し方
- マージ判断を依頼する条件。CI 待ちならその旨

Issue 側にも PR リンクを追記する。全完了条件を満たしてマージで解決する Issue にだけ `Closes #番号` を使う。一部対応なら `Refs #番号` 等で関連付け、未解決部分を誤って自動終了させない。PR 本文更新では他者の追記を保持する。

## コメント・レビュー・CI
- 実質的な変更、新しい根拠、重要な失敗、解決、判断依頼があるときだけコメントする。同じ SHA・結果・判断を重複投稿しない。既存コメントと本文を読み、軽微な進捗は本文の更新へまとめる。
- レビュー指摘はソースと証拠に照らして検証し、妥当なら最小修正、不一致なら根拠を示す。指摘、対応、未解決を追跡し、未確認を解決済みにしない。
- CI 失敗は該当 SHA・stage・ログを確認する。依頼範囲内の軽微な不具合なら自律修正、commit/push、再検証する。大きな変更など承認境界に達した部分だけ保留する。
- 同じ失敗の無根拠な rerun や、期待値を弱めて成功扱いにする変更はしない。環境の一過性と判断して再実行した場合も初回失敗と根拠を残す。
- 最終 head の CI を terminal state まで確認し、古い SHA の成功を流用しない。設定や保護を変更して失敗を回避しない。

## 完了報告と人間のマージ後
利用者には PR URL、最終 SHA、短い変更概要、検証結果・CI URL、残存リスク、マージ可否の推奨を届ける。原則として利用者に残す操作はレビューとマージ判断とする。権限上の不足があれば対象と必要な判断だけを尋ねる。

エージェントはマージしない。人間のマージを確認後、関連 Issue の受入条件・解決状況を照合する。全解決なら根拠付きで終了し、一部未解決なら Issue を維持するか、残件の別 Issue と相互リンクを作り、解決済み範囲を明記する。マージされたという事実だけで全要件解決と判断しない。無関係な既存 Issue をまとめて閉じない。ローカル main の同期は環境への実際のアクセスと依頼範囲を確認して行い、同期したと推測しない。
