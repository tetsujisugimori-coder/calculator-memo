# JSONバックアップの安全な全体復元（Issue #108）

## 対応形式と受入条件

`calculator-memo-backup` version 1、`calculation-memo:data` 保存形式 version 1 を1件丸ごと置換する。統合、部分復元、参照IDの再割当て、同期、暗黙の移行・修復はしない。ファイル選択とプレビューは読取専用。元raw文字列を直接書き、解析値から再構成しない。

外側JSONと内部rawを分けて検証する。形式名・version・captured・対象キー1件・原文型/UTF-16長・appStorageVersion・validation・主要件数・取得/作成日時の整合を確認する。全階層の重複キー（エスケープで同名になるキーを含む）、深さ128超過、16 MiB超のファイル、2 Mi UTF-16コード単位超の原文を拒否する。ファイルの拡張子/MIMEは選択ヒントであり信頼しない。

現行loadData受理だけでは不十分。入力とロード結果を構造照合し、履歴除外や設定補正が起きる入力を拒否する。履歴必須フィールド/一意ID/有限結果、履歴とメモの表示に必要な日時を検証する。未知フィールドや未知数値字句はrawに保持する。ただし未知形式version・壊れた原文は、書き出せても復元には使用できない。数学的正しさ・参照先の現存性・真正性は検証しない。旧形式が表示のため補正を要する場合も、この第一段階では自動修復せず拒否する。

## 利用手順と比較

「JSONから復元」→ファイルを選択→現在/復元予定の件数・原文長・状態・作成/取得日時を確認→「現在データを保全する」→全体置換の承認チェック→「復元を実行する」。件数不明はUNKNOWN、キーなし/破損/未知versionを区別する。件数が同じでも内容一致とはせず、raw全体の完全一致/相違を別表示する。

ファイル取消/差替え、通知、確認後変更は承認を失効する。Enterでは実行しない。最終ボタンの明示タップ/クリック、またはフォーカスしてSpaceで実行する。二重操作と実行中の閉鎖を抑止する。未保存/保存待ち/編集画面がある場合は復元を停止し、内容を自動保存・破棄しない。

## 復元前原文の保全

専用キー `calculation-memo:restore-recovery:v1:0` ～ `:7` に独立したimmutableコピーを追加する。各コピーは形式/version/取得日時/元キー/原文/原文長を保持し、キー不存在はraw:nullとして区別する。既存slotを上書き・削除しない。同じrawの検証済みコピーが既にあれば、再読照合して再利用できる。

合計4 Mi UTF-16コード単位（record JSONの長さ）、最大8件、各原文2 Miまで。ブラウザの実際のquotaはこの上限とは異なり、上限未満でも失敗し得る。空き不足、破損/未知record、読取失敗、set失敗、読戻し不一致ではデータキー上書きを拒否する。実行直前にもコピーのrecord文字列と現在rawの一致を確認する。ダウンロード開始や承認ボタンでこの条件を迂回できない。

コピーはブラウザ保存が消去されるまで無期限保持し、自動清掃・削除UIは設けない。満杯なら今回の復元を停止し、古いコピーを勝手に捨てない。私的な原文を含むため、共有端末やサイトデータ管理に注意する。これは別キーへの保全であり、別の物理媒体への永続保証ではない。サイトデータの全消去・端末故障・保存領域自体の喪失では現データと同時に失われ得る。

再起動後も「保持中の復旧コピー」から各原文を既存backup形式で個別にダウンロード要求できる。正常なコピーは同じ入力検証・全体復元手順で戻せる。未知/破損のコピーは証拠として書き出せるが自動修復や復元の許可とはしない。raw:nullはキー欠落の記録であり復元用JSONはない。ダウンロードイベントは端末への保存完了を証明しない。

通常の「データのバックアップ」が対象とするのは従来どおりデータキーだけ。復旧slotを通常バックアップへ再帰収集したり、復元先として受理しない。復旧slotには上記の個別書出し導線を用いる。他アプリのキーは探索しない。

## 競合・書込み・画面

現在のアプリの保存と共有するWeb Lock/同一タブqueueを使う。復元画面中は通常保存を凍結し、待機中の保存callbackも同期refを再確認する。プレビューのraw・アプリ世代・ファイル世代・承認・copyを実行直前に照合し、1回だけsetItemしてrawを読み戻す。別タブの同値通知/clear通知も承認を失効する。同一タブのアプリ状態変更は同期世代で検出し、通知のないraw変更も直前比較で拒否する。

setItemを呼ぶ前に「書込み試行済み」と記録する。例外が書込後に起きる可能性を排除せず、読戻し不一致/失敗・確認状態失効はUNKNOWNとする。自動再試行・自動rollbackをしない。他のwriterの新しい原文を巻戻しで消すことは避ける。元コピーは保持する。

原文一致を確認した後、新しいメモリ状態とclean baselineを一緒に適用する。未変更の起動時/復元直後はrawを再serializeせず、空白・巨大数値字句を維持する。既存のキー不存在時の初期化は維持する。通常の明示的編集に伴う既存保存は引き続きJSON再serializeであり、一般のlossless JSONエディタに変更したわけではない。

画面更新が確認できない場合も自動保存を停止し、復旧copyと現在rawの書出し、明示再読込を案内する。復元のみで計算・履歴追加・確認記録・snapshot・レポート本文の変更を行わない。

localStorageにCAS/全体transactionはない。古いクライアント、直接書込み、通知前/比較間のABA、readback後の他writer、ディスク永続化は完全保証できずUNKNOWNの残余である。Web Locks非対応時は同一タブqueueのみで、別タブの協調ロック保証はない。

## Safari・検証境界

ネイティブinput type=fileとFile読取り、Blob/downloadを使い、File System Access APIやクラウド送信に依存しない。[Appleの互換性文書](https://developer.apple.com/library/archive/documentation/AppleApplications/Reference/SafariWebContent/CreatingContentforSafarioniPhone/CreatingContentforSafarioniPhone.html) はiOSのファイル入力対応を説明し、[Safari 18.4のWebKit発表](https://webkit.org/blog/16574/webkit-features-in-safari-18-4/)にもファイル入力機能が記載される。これは現在の実機/ファイル提供元の動作確認の代替ではない。読取不能時は端末内へファイルを保存して再選択できるが、その成功は実機で未検証。

独立GUIはChromium/WebKit×375/390×light/darkの8条件、CSS200%、touch、プレビュー/比較/保全/承認/成功・失敗、長い名前、横幅、44px目安を検証する。正式GUIの6条件・1128検査・592geometry・132PNG・touch各1337・3workers・30分は不変更。既知WebKit遅延はIssue #105で分離する。実機iPhone Safari、VoiceOver、OS文字拡大、OSファイルピッカー、端末保存完了、長期保持は未検証。実測・最終HEAD・成果物・独立レビューはPR記録で示す。
