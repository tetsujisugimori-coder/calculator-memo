## Aborted initial database enumeration: oracle correction

The first pinned-WebKit CI failed this reviewer's assertion that `indexedDB.databases()` must omit the name after an aborted initial open. This is separate from the session-lifetime adapter defects. The author's independent native reopen probe in that same first CI observed an absent/uninitialized database on both engines; original CI artifacts remain the source of those observations.

Primary upstream evidence explains a known compatibility case: [WebKit bug 313922](https://bugs.webkit.org/show_bug.cgi?id=313922) and [WebKit correction fe33814](https://github.com/WebKit/WebKit/commit/fe33814c6298e5e9828424880df19def4b97a889) describe version correctly reverting to 0 while database-name enumeration still included it. That fix landed May 2026. Applying it to the older pinned Playwright WebKit is an inference; this review does not claim to have patched or upgraded that engine. The [IndexedDB specification](https://www.w3.org/TR/IndexedDB/#dom-idbfactory-databases) also describes enumeration as a snapshot without ordering guarantees relative to create/upgrade/delete requests.

The independent oracle now retains native enumeration diagnostically and directly probes the protocol state: opening after the reader must trigger `upgradeneeded` with **oldVersion 0 and no object stores**, followed by an explicitly aborted probe upgrade. A separately initialized synthetic database is the positive control: the identical probe must observe ordinary success at **version 1 with exactly `records`**, so an accidentally initialized or upgraded reader cannot pass. The probe is test-only; it aborts its own creation attempt and does not use the implementation inspector to decide whether a committed schema exists. This change verifies the application's no-initialization/no-upgrade property; it no longer asserts that an engine cannot retain an aborted version-0 catalog placeholder. Local Chromium passed the stronger oracle; final pinned-WebKit CI must execute it anew.
